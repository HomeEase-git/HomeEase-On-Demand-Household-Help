# Deploying HomeEase

Chosen stack: **Render** (backend + Redis), **Neon** (Postgres, kept — not
Render's managed Postgres), **Vercel** (admin web), **EAS** (mobile).

| Unit | Tech | Hosted on | Serves |
|------|------|-----------|--------|
| **backend** | Express 5 + Prisma 7 + BullMQ + Socket.IO | Render (`render.yaml` Blueprint, `backend/Dockerfile`) | REST API `/api/*`, websockets, background workers |
| **web** | Vite + React (admin dashboard) | Vercel (static, `web/vercel.json`) | Admin UI |
| **mobile** | Expo / React Native | EAS build → `.apk` / store binary | Clients & workers |
| Postgres 16 | — | **Neon**, production branch (separate from the dev one) | primary datastore |
| Redis | — | Render Key Value (`homeease-redis` in `render.yaml`) | BullMQ job queues |

`backend/Dockerfile` + `docker-compose.yml` still exist and still work — they're
the local-rehearsal / VPS-fallback path (§5), not the primary one.

The backend **requires** both Postgres and Redis. Without Redis it still answers
HTTP, but every background flow silently stops: payout disbursement, the 72h
overdue-payment → auto-dispute sweep, quote / completion timeouts, and payment
reminders. Treat Redis as a hard dependency and watch `GET /health/ready`.

## 1. Provision first

- **Neon** — done: project **`homeease-prod`** (`quiet-pond-70953688`), AWS
  `ap-southeast-1` (matches Render's Singapore region), Postgres 18, branch
  `main`. Kept separate from the dev project (`floral-lake-80894687`, us-east-1).
  All 44 migrations already applied to it via `prisma migrate deploy`; Render
  re-runs `migrate deploy` on every deploy anyway (idempotent). Pull the two
  connection strings from the Neon console (or `neonctl connection-string`):
  `DATABASE_URL` = the **-pooler** host, `DIRECT_URL` = the plain host.
  Free-tier caveats to revisit before real traffic: compute is fixed at
  0.25 CU (raise the max in the console), suspends after ~5 min idle (Render's
  `/health` check doesn't keep it warm), and history retention / PITR is 6h only.
- **Render account**, repo connected — the Blueprint (§2) provisions the web
  service + Redis together.
- **Vercel account**, repo connected, Root Directory set to `web`.
- **Supabase** project + storage buckets: `kyc-documents`, `resumes`,
  `chat-images`, `avatars`, `booking-photos`, `tax-certificates` (the backend
  calls `ensureStorageBuckets()` on boot and will create missing ones if the
  service key allows it).
- **Xendit** — a **live** secret key (`xnd_production_…`) and a webhook token.
  Point the Xendit dashboard webhook at `https://<render-url>/api/payments/xendit/invoice-webhook`
  and `.../payout-webhook` (see `backend/src/routes/payments.ts`).
- **SMTP** (Gmail app password) and **PhilSMS** token + approved sender ID.
- **Anthropic API key** (resume parsing / KYC assist) — optional; leave blank to disable.
- **DNS** (optional at first) — Render and Vercel both work fine on their
  `*.onrender.com` / `*.vercel.app` subdomains; add custom domains later.

## 2. Backend — Render

1. Push `render.yaml` (repo root) if not already on the branch you deploy from.
2. Render dashboard → **New → Blueprint** → select this repo/branch. It reads
   `render.yaml` and creates `homeease-backend` (web service) and
   `homeease-redis` (Key Value) together.
3. Render prompts for every `sync: false` var in the Blueprint: Neon's
   `DATABASE_URL`/`DIRECT_URL`, Xendit live keys, Supabase keys, SMTP, PhilSMS,
   platform legal name/TIN. Fill them in.
4. `JWT_SECRET` is auto-generated by Render (`generateValue: true`) — you never
   see or set it directly. `REDIS_URL` is wired automatically from the
   `homeease-redis` service.
5. **Second pass, after the first deploy succeeds:** Render assigns
   `homeease-backend` a URL (`https://homeease-backend-xxxx.onrender.com`).
   Go back into its environment settings and set:
   - `APP_URL` → that URL
   - `ALLOWED_ORIGINS` → the Vercel admin-web domain (from §3), comma-separated
     with anything else that needs CORS access

   Both changes trigger a redeploy.
6. Confirm the plan is **not** `free` on the web service (see the comment in
   `render.yaml` — the in-process background workers need always-on).

### Probes
- **Liveness:** `GET /health` → `200 {"status":"OK"}` (no dependencies touched).
- **Readiness:** `GET /health/ready` → `200` when Postgres is reachable, `503`
  otherwise.

### Shutdown
The server drains on `SIGTERM`/`SIGINT`: stops accepting connections, finishes
in-flight requests, closes websockets + BullMQ workers/queues, disconnects
Prisma, then exits. Budget is `SHUTDOWN_TIMEOUT_MS` (default 15s).

### First-run data
Neither the image nor the Blueprint ships seeds. After the first deploy,
create via the admin dashboard (or a one-off `npm run prisma:seed:complete`
pointed at the prod DB): service types, pricing rules, and the `AppSettings`
row (commission + withholding rate). Create the first `ADMIN` user directly in
the DB or with a seed script.

## 3. Web (admin dashboard) — Vercel

1. Vercel dashboard → **New Project** → import this repo.
2. **Root Directory:** `web` (the build still resolves `../shared` — Vercel
   checks out the full repo and runs the build from this subdirectory).
3. Framework preset: Vite (auto-detected; `web/vercel.json` pins the build
   command/output dir and adds the SPA rewrite + a couple of security
   headers).
4. Set env var `VITE_API_URL` to the Render backend's URL **with `/api`**,
   e.g. `https://homeease-backend-xxxx.onrender.com/api`. This is cross-origin
   (Vercel ≠ Render), unlike the docker-compose same-origin nginx-proxy setup
   — that's why `ALLOWED_ORIGINS` on the backend (§2 step 5) matters here.
5. Deploy. Grab the resulting `*.vercel.app` URL and feed it back into the
   backend's `ALLOWED_ORIGINS` if you haven't already.

## 4. Mobile

`mobile/eas.json` carries `EXPO_PUBLIC_API_URL` per profile — **replace the
`REPLACE_ME` placeholders** with the Render backend URL (`https://…onrender.com`,
no trailing slash).
```
cd mobile
eas build --profile production --platform android
```
`app.json` is already set: package `com.homeease.app`, EAS project linked,
camera / location permission strings present.

## 5. Local rehearsal / VPS fallback (docker-compose)

Not the deploy path above — this is for testing the containers locally, or as
a fallback if you ever move off Render to a plain VPS.
```
cp backend/.env.example backend/.env    # fill in real secrets
docker compose up --build
```
Brings up Postgres + Redis + backend (auto-migrated) + web (via
`web/Dockerfile`'s nginx image, not Vercel). Admin on `http://localhost:8080`,
API on `http://localhost:3000`. Compose overrides `DATABASE_URL` / `REDIS_HOST`
to the container services regardless of what `backend/.env` says; secrets
still come from `backend/.env`.

## 6. Post-deploy smoke test

1. `curl https://<render-url>/health` → `200`
2. `curl https://<render-url>/health/ready` → `200`
3. Vercel admin dashboard loads, login works, calls reach the Render API
   (check the browser network tab for CORS errors first if not).
4. `prisma migrate status` against the Neon prod branch → "up to date".
5. Register a client + worker on mobile against the Render API.
6. Run one full booking → completion → **payment** cycle end to end and
   confirm the Xendit invoice + payout land. This path has not been exercised
   against live Xendit yet — do it in a controlled test before real traffic.
7. Kill/restart the Render Key Value instance and confirm the API stays up
   (`/health` 200) while `/health/ready` still reports the DB fine; confirm
   workers reconnect once Redis is back.

## Not done yet (do before real users)

- **Live payment verification.** The pay-after-completion flow (invoice →
  `AWAITING_PAYMENT` → payout with debt-netting → 72h auto-dispute) has never
  run against real Xendit. Step 6 above is mandatory.
- **Structured logging.** Everything is `console.*`. Add a real logger + log
  aggregation before you need to debug production.
- **Error tracking / metrics / uptime alerting.** None wired.
- **Backups.** Confirm Neon's automated backup/PITR settings on the prod
  branch and do one test restore.
- **Secrets rotation.** `JWT_SECRET` rotation invalidates all sessions — plan for it.
- **Load test** the rate-limit ceilings (`RATE_LIMIT_*`) against expected traffic.
- **`homeease-redis`'s `ipAllowList`** in `render.yaml` is wide open
  (`0.0.0.0/0`) — tighten it once you've confirmed Render's private-network
  behavior for Key Value services.

CI is green as of PR #4 (backend, docker, mobile, web all pass on every push) —
that gate is done; keep it green on whatever branch you deploy from.
